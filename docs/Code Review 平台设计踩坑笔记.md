## 1. Agent Review：限制探索，但不能打断正确思考

### 1.1 设计过程遇到的问题

Agent Review 可以主动搜索和阅读源码，但也容易为了“再确认一下”不断扩大范围。

Run 18 已经把最大回合数提高到 12，却仍然在调用 20 次工具后没有提交结果。这说明真正的问题不是
时间不够，而是 Agent 不知道什么时候应该停止检索。

本地 Agent 有用户在旁边观察和纠偏，服务器 Worker 则是无人值守运行。如果完全放开，单个任务可能
长时间占用模型和队列；如果突然强制中断，又可能让 Agent 在证据不足时草率下结论。

### 1.2 考虑的设计方案

考虑过三种做法：

1. **继续提高回合和工具上限**：只能让发散持续更久，没有解决根因。
2. **只在 Prompt 中提醒及时提交**：属于软约束，模型仍可能继续搜索。
3. **Prompt 引导加工具侧收敛**：既告诉 Agent 怎样审查，也由平台保证最终能停下来。

最终采用第三种方案：

```text
先看 diff
→ 最多提出 3 个风险假设
→ 只围绕假设定向取证
→ 提前提示收敛
→ 完成当前取证
→ 保守提交 Review Card
```

核心设计点：

- 标准 Agent Review 使用 `high` 推理强度，`max` 留给后续深度审查评估。
- 第 8 次证据调用开始提醒收敛，第 10 次证据调用仍正常完成。
- 第 11 次起拒绝新增证据读取，但不会中断正在执行的第 10 次调用。
- `submit_review` 独立预留，不因证据预算耗尽而不可用。
- 证据不足时允许 `PARTIAL/INSUFFICIENT` 或空 findings，不能为了完成任务编造问题。
- 页面只展示脱敏阶段时间轴，不保存源码、Prompt 或模型完整思维链。

这里最重要的取舍是：

> 预算不足可以降低复杂问题的召回，但不能用未经验证的假设换取表面上的“完整审查”。

### 1.3 最后验收成果

当前状态：**设计完成，待实现、待真实任务验收。**

第一次只选择 1～5 个非敏感文件的小型任务，验证 Agent 能成功提交、落库并展示脱敏轨迹。首次成功
后停止，不直接用 Run 18 等复杂任务扩大范围。

详细设计见 `docs/44-agent-review-local-like-convergence-plan.md`。

## 2. 普通 Review 高准确模式：先准备证据，再让模型判断

### 2.1 设计过程遇到的问题

普通 Review 是一次模型请求。模型不能像 Agent 一样临时搜索仓库，它只能看到平台提前放进请求的
diff 和上下文。

只把 diff 发给模型会产生两个问题：

- 调用方、字段引用、Mapper、缓存读写和配置等关键证据可能缺失，造成漏报。
- 模型容易把“没有看到引用”误解成“没有引用”，造成无证据结论或误报。

但把整个仓库全部塞给模型同样不可行：输入成本高、噪声大，还可能让真正相关的证据被淹没。

### 2.2 考虑的设计方案

高准确模式没有选择“无限增加上下文”，而是设计了一条受控证据链：

```text
确定性检查
→ Context Planner 判断需要什么证据
→ Local Retriever 定向检索
→ Context Pack 按优先级装入有限证据
→ 模型一次性审查
→ 人工反馈和评估验证结果
```

核心设计点如下。

#### 先区分事实和模型判断

敏感信息扫描等确定性检查先于模型执行。同一次多模型调度复用同一份检查结果，检查失败时保留脱敏
原因并继续 Review，不把工具故障误当成代码安全。

#### 只检索与当前风险有关的上下文

Context Planner 根据 changed files、diff、端类型和变更信号判断需要调用方、字段引用、数据库、
缓存或配置中的哪类证据。Local Retriever 只做定向检索，不默认扫描并注入整个仓库。

#### 预算裁剪必须可解释

Context Pack 按证据价值和预算装入内容。超出预算的证据会标记为 `BUDGET_CUT` 或
`notInjectedEvidence`。

这表示“平台没有把这份证据交给模型”，不能被解释成“代码中不存在这份证据”。

#### 结论必须说明证据是否充分

每个 finding 都需要包含：

- `contextStatus`：证据充分、部分充分或不足；
- `confidence`：模型对结论的置信度；
- `evidence`：已经看到的依据；
- `missingContext`：仍缺少什么上下文。

当模型只能基于 diff 推断时，应使用 `PARTIAL/INSUFFICIENT` 和 `LOW/MEDIUM` confidence。缺少证据
时原则上不报告；只有潜在影响很高时，才作为“需要人工确认”的低置信度问题保留。

#### 不自动篡改原结论

对于高影响但证据不足的 finding，用户可以触发“补证据”。新增证据作为独立覆盖层展示，不直接修改
原 finding，也不自动降低等级、自动忽略或自动改变通知结果。

#### 用评估数据决定是否继续增强

多模型可以扩大覆盖面，但“多调用一个模型”不等于真正的高准确。高准确模式最终依靠人工评估样本、
回放、质量看板和验收记录判断：

- 是否减少误报；
- 是否减少漏报；
- 上下文不足是否下降；
- 增加的耗时和成本是否值得。

没有评估样本证明的 Retriever 或 Prompt 改动，不应仅凭直觉进入主线。

### 2.3 最后验收成果

当前普通 Review 高准确模式已经具备：

- Review 前确定性检查及多模型复用；
- Context Planner、Local Retriever 和有限 Context Pack；
- 预算裁剪与未注入证据说明；
- `contextStatus / confidence / evidence / missingContext` 结构化结果；
- 高影响且上下文不足 finding 的人工补证据入口；
- 评估样本、回放、质量看板、缺口归因和改动验收记录；
- 任务详情中的高准确模式执行过程展示。

当前边界也需要保留：

- 普通 Review 仍是一次模型请求，不能动态调用源码工具。
- 不同端的专项 Retriever 完整度不同，不能把已有 Java 关系检索能力等同于所有语言都已覆盖。
- 工程能力落地不等于准确率已经得到充分证明，仍需要真实样本持续计算误报、漏报和上下文不足。

核心成果可以概括为：

> 普通 Review 不再只给模型一段 diff，而是给它一份有来源、有预算、有缺失说明的证据包；模型也不能
> 只给结论，必须同时说明证据和不确定性。
