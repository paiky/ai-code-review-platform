这是当前code review平台的任务详情页，当前布局不够聚焦：

1. 页面进来不能一眼看到review结果，不够重点
2. 时间轴阶段展开不够明细，不够明确



你觉得可以如何调整？





我同意你现在的判断。当前页面的问题不是“信息不够”，而是**结果、过程、运行元数据同时争夺第一视觉层级**。

我会把这个详情页重新定义成：

> **先回答「这次 Review 发现了什么」 → 再回答「为什么这么判断」 → 最后回答「Agent 是怎么跑出来的」。**

也就是从现在的“任务执行详情页”，改成真正的 **Review 结果详情页**。

------

## 一、当前页面最明显的 4 个问题

### 1. Review 结果出现得太晚

现在进入页面后首先看到的是：

任务标题 → 任务元数据 → Agent Review 执行摘要 → 巨大的「Review 已完成」卡片 → 阶段轨迹 → 最后才是质量问题。

但对于使用者而言，最想知道的是：

**有没有问题？严重吗？是什么问题？**

所以现在真正重要的：

> ```
> 2 个问题 / 1 高风险 / 1 中风险
> ```

反而被埋到了第二屏。

------

### 2. 「已完成」这个信息重复了太多次

现在至少有：

- 顶部 `已完成`
- 黄色提示「发现 2 个代码质量问题」
- 大型绿色 `Review 已完成`
- 时间轴每个节点 `已完成`
- Drawer 又显示 `已完成`

其中最明显可以删除的是这张：

> 🧠 Review 已完成
>  正式结果已保存……

它占用了非常大的视觉面积，却几乎没有新增信息。

**建议直接删除整个绿色完成卡。**

完成状态只需要在顶部 Review 结果摘要里表达一次。

------

### 3. 当前时间轴更像“流程导航”，不像“Review Trace”

现在：

```
排队与调度 → 确定性预检 → 模型 Review → 成功/失败/fallback 终态
```

这个作为一级流程没有问题。

但点击进去后，你真正想看的应该是：

> Agent 当时做了什么？

而现在 Drawer 主要还是各种字段：

- Review 引擎
- Provider/model
- Run
- 工具调用
- 源码返回
- 模型回合

这些是**统计数据**，不是**运行轨迹**。

所以才会产生“展开了还是不够明确”的感觉。

------

### 4. 结果和 Trace 的视觉权重反了

你做这个 Trace 是有价值的，因为后面你需要：

- 定位误判来源
- 判断证据是否充分
- 看 Agent 调用了什么工具
- 看模型为什么得出某个 Finding
- 调优 Prompt / Agent 策略

所以 **Trace 不能删。**

但是：

> **Trace 是诊断信息，不应该压过 Review Result。**

# 十一、我最推荐的最终信息架构

整个详情页最终只保留 4 个一级区域：

第一屏最核心。

```

页面主体，视觉权重最高。

用于复盘 Agent。

```

最底层。

```

```

## 第一屏应该最终变成这样

你现在第一屏大概是：

```

Task Metadata              22%
Review Runtime Summary     22%
Review 完成 Hero           30%
────────────────────────────

```

这是我认为这次改版最重要的一条验收标准。

另外一个我会坚持保留的设计是：

**不要把 Review Trace 删除。**

只是把它从“页面主角”降级成“可追溯诊断能力”。你的平台以后要做 Agent 调优、误判复盘、证据完整性分析，Trace 会越来越重要。现在真正需要改的是它的表达方式——从「阶段字段详情」升级成「Agent 行为事件流」。
