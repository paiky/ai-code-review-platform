这次评估我认为已经把方案从“产品设计建议”进一步收敛到了**可以进入工程计划设计的程度**。尤其有三处修正非常关键：`findingIndex` 不能因视觉排序被破坏、Safe Trace 不能制造伪精确时间、Trace 中不能把 `itemCount` 包装成“证据数量”。这些都应该以这版结论为准。

我建议直接接受最后三个产品决策：

1. **Finding 不重新排序原数组，只默认展开最高风险 Finding。**
2. **Safe Trace V1 只显示序号，不显示事件发生时钟。**
3. **顶部只提供“查看 Review 流程”，滚动到六阶段，不新增全局 Trace Drawer。**

其中第 1 条还建议进一步固化成一个前端原则：

```
displayFindingIndex ≠ findingIndex

所有写操作 / API / Deep Link：
永远使用服务端原始 findingIndex

UI：
可以计算 highestRiskOriginalIndex
但不能通过 sort() 改变 findings 的索引语义
```

这样以后即使真的要做风险排序，也不会再次踩这个坑。

## Phase 1 我建议最终收敛成这个范围

这一步不要再夹带 Trace 重构。

### 页面结构

```
紧凑任务头
↓
多 Review 选择器（存在多个 Review 时）
↓
Review 结果摘要
↓
Findings
↓
Review 流程（现有六阶段）
↓
Task Metadata
```

### Review 结果摘要

成功状态：

```
Review 完成

发现 2 个代码质量问题

[紧急 0] [高风险 1] [中风险 1] [低风险 0]

review.summary 正式摘要……

Agent Review · DeepSeek
总耗时 181s

                    [查看 Review 流程 ↓]
```

这里我赞成评估里的提醒：

**181s 必须明确是什么耗时。**

例如：

- `review.startedAt → review.finishedAt`：显示「总耗时」
- `agentRunSummary.durationMs`：显示「Agent 耗时」

如果两个都有，可以：

```
总耗时 181s · Agent 执行 180s
```

没有则隐藏，而不是 `0s`。

## Finding 默认展开规则需要再精确定义一下

建议风险权重独立建立：

```
CRITICAL        → 4
HIGH / MAJOR    → 3
MEDIUM / MINOR  → 2
LOW             → 1
未知             → 0
```

然后：

```
遍历原 findings
↓
找 severityWeight 最大值
↓
相同风险取原始数组中第一条
↓
得到 highestRiskFindingIndex
↓
默认 expanded
```

**不改变数组顺序。**

因此用户看到的顺序仍然完全尊重正式 Review Card，只是默认帮他打开最值得关注的那一项。

这其实比“把高风险问题移动到最前面”更加稳健。

------

# 六阶段也不要为了第一屏强行压缩

这里我也赞成这次评估对我之前建议的修正。

正确目标不是：

> 六阶段必须 80～110px。

而是：

> 六阶段在桌面环境下尽量单行、降低视觉重量，但允许响应式换行。

例如 1440：

```
✓ 排队与调度
  0.3s
      ───
✓ 确定性预检
  0.8s
      ───
✓ 上下文准备
  3.2s
      ───
✓ 模型 Review
  180s
      ───
✓ 解析与保存
  0.6s
      ───
✓ Review 完成
  -
```

小屏则：

```
排队 → 预检 → 上下文
模型 → 保存 → 完成
```

不应该为了“首屏目标”破坏流程可读性。

# Phase 1 的终态分支最好现在就写成明确规则

这是开发计划里非常值得补的一块。

### SUCCESS

```
✓ Review 完成
2 个问题
正式 summary
风险统计
```

删除现有大型完成 Hero。

### FAILED

```
✕ Review 失败

Agent Review 未能生成正式结果
失败原因：……

[查看 Review 流程]
```

不能进入 Findings 优先模式，因为可能根本没有正式 Findings。

### CANCELLED

```
Review 已取消

任务在模型 Review 阶段被取消
```

### SKIPPED

```
Review 已跳过

跳过原因：……
```

### FALLBACK

这类尤其不能被压成一个普通 SUCCESS：

```
Review 完成 · 已降级

Agent Review
    ↓ 执行失败
Standard Review
    ↓
✓ 生成正式结果
```

结果摘要展示最终正式 Review，但必须保留 fallback 来源。

# Safe Trace V1，我建议再砍掉一点野心

这次评估之后，Phase 2 的正确定位已经不是：

> Agent 到底逐秒做了什么。

而是：

> **系统能够安全证明 Agent 做过哪些类型的动作。**

所以模型 Review Drawer 可以做成：

```
模型 Review
Agent Review · 已完成
Agent Run #129
Agent 耗时 180s


运行记录

#1  分析变更
    已完成

#2  读取源码片段
    已完成 · 12.8s
    返回 21850 bytes

#3  搜索代码上下文
    已完成 · 4.6s
    返回 12 条目

#4  读取源码片段
    已完成 · 7.2s
    返回 8430 bytes

#5  提交 Review Card
    已完成


运行配额
工具调用       7 / 40
证据调用累计   6 / 15
源码返回       21850 / 200000 bytes
模型回合       8 / 18
提交尝试       1 / 3
```

注意这里的措辞：

- `12 条目`，不是 12 条证据；
- `证据调用累计 6`，不是获得 6 条证据；
- 不出现伪造时钟；
- 不显示参数；
- 不显示查询词；
- 不显示实际路径；
- 不显示源码；
- 不显示模型 reasoning。

这样产品表达和数据语义就对齐了。

# Phase 2 最重要的不是 UI，而是白名单 ViewModel

这一点评估也非常重要。

不要：

```
Progress Detail
    ↓
Drawer 直接解析
    ↓
展示
```

应该明确隔一层：

```
原始 Agent Progress
        ↓
ReviewJourney 安全派生
        ↓
SafeTraceEvent[]
        ↓
Drawer
```

例如前端内部只允许拿到：

```
SafeTraceEvent
- sequence
- activityType
- displayLabel
- status
- durationMs
- itemCount?
- byteCount?
- budgetUsed?
```

**没有 `detail`、没有 query、没有 path、没有 input/output。**

那么以后即使原始 Progress 新增敏感字段，也不会意外直接进入 UI。

我甚至建议把这一条作为 Phase 2 的安全验收项，而不是普通实现细节。

# Phase 3 确实应该拆掉

不要再叫一个笼统的：

> Phase 3：Evidence Contract

至少拆成：

```
Phase 3A
Typed Evidence Domain Model
小/中

Phase 3B
Review Card ↔ Evidence 持久化关联
中

Phase 3C
Evidence API / backward compatibility
中

Phase 3D
Finding Evidence UI
中

Phase 3E
Evidence Chain Visualization
中
```

每一阶段都可以独立：

> 实现 → 测试 → 验收 → 停止

这样也符合你现在项目本身越来越强调的“不要让 Agent 一口气做大阶段”的工程方式。

## 关于 1440×1000 的验收标准，我建议采用

这个比“桌面首屏”清晰很多。

最终可以定成：

> **在 1440×1000 viewport、浏览器缩放 100%、成功终态且存在 Finding 的情况下，不滚动页面即可看到：Review 状态、问题总数、风险分布、正式 `review.summary`，以及默认展开的最高风险 Finding 的标题、位置和问题正文开头。**

再补一句：

> 不要求首屏完整展示 Finding 建议、证据摘要和 Review 六阶段。

这样验收就很稳。

否则开发为了满足“全部首屏”很容易再次把页面压得非常拥挤。

------

所以现在 `调整1.md` 的定位我会明确区分：

**它继续作为 UX / 产品方向文档是合格的；下一步不要继续往里面堆实现细节，而应该基于它单独形成一份 Phase 1 Implementation Plan。**

Phase 1 Plan 重点写清楚：

```
现状 → 目标布局 → 数据字段来源 → 状态分支 → findingIndex 约束 → 响应式 → 验收场景 → 非目标 → 停止点
```

这样 Codex 拿到的是一个真正能执行的工程计划，而不是让它自己从 UI 设计文档里推断实现边界。
