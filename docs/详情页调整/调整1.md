这份评估比我上一版建议更适合直接进入开发，尤其是把**产品体验目标**和**现有数据契约 / Trace 安全边界**分开了。我基本同意，可以据此收口方案。

我会把最终方向定成一句话：

> **终态详情页从“执行过程展示页”改成“Review 结果页”，Trace 作为可追溯诊断能力下沉，但不削弱。**

### 四个产品决策可以直接定下来

1. **继续遵守 Trace 安全白名单。**
    当前详情页没必要为了“轨迹看起来更真实”暴露查询词、源码、具体工具参数、模型输入输出。纵向 Trace 仍然值得做，但展示粒度控制成：
    `时间 → 活动类型 → 状态 → 耗时 → 数量`

   例如：
    `15:29:28 · 读取代码上下文 · 完成 · 12.8s · 返回 3 条证据`

   而不是展示实际搜索内容。

2. **最高风险 Finding 默认展开。**
    这个我认为应该作为本轮明确产品规则，而不是可选优化。否则即使把 Findings 提到第一屏，用户看到的依然只是两个标题，改善会打折扣。推荐排序：
    `CRITICAL/高 → MAJOR/中 → MINOR/低 → 置信度 → 原始顺序`。

3. **本轮不做真正的“证据链”。**
    现在已有的 `contextSummary / evidence / missingContext` 可以重新排版成：

   ```
   判断依据
   · Evidence 1
   · Evidence 2
   · Evidence 3

   上下文状态
   已获取：……
   仍缺少：……
   ```

   这叫**证据摘要**比较准确，不要包装成“因果链”。真正的 `Diff → Symbol → Caller → Data Model → Finding` 应该等 typed evidence contract。

4. **Task Metadata 使用页面内折叠，不使用 Drawer。**
    这个判断是对的。Drawer 应该留给 Trace 这种需要集中阅读的诊断信息。任务元数据本质上仍属于页面上下文，只是视觉降级。

## 本轮还有两个应该顺手修掉的问题

第一是你提到的：

> Review 已成功，但「收敛结论」仍为等待中。

不要单纯在前端粗暴写成“终态 SUCCESS → 所有子阶段 SUCCESS”。

更稳妥的是：

```
存在明确事件
→ 使用事件状态

不存在明确事件，但后续存在可靠完成事件
→ 不显示该子阶段 / 显示“已随 Review 完成”

不存在任何可证明状态
→ 不展示
```

**宁可少显示，也不要推导出虚假的执行精度。**

第二是耗时：

```
durationMs != null
→ 180s / 3.2s / 742ms

durationMs == null
→ -

不要：
单事件 → <1s
success → 0s
```

这个原则也建议以后整个 Agent 可观测性 UI 都统一使用。

## 我会把实施范围严格切成 3 层

**Phase 1 现在就做：终态信息架构重构。** 不改后端：删除成功 Hero、压缩 Header/Metadata、加入 `review.summary`、风险统计、Findings 提前、最高风险默认展开、现有六阶段视觉压缩、修正不可靠状态表达。

**Phase 2 再做：Safe Trace。** 继续沿用安全白名单，把 Drawer 从“字段表”升级为脱敏纵向事件流，高级运行指标折叠。

**Phase 3 单独立项：Review Evidence Contract。** typed evidence、证据来源类型、Symbol/调用关系、Finding↔Evidence 关联、真正的证据链，以及如果确实有需求，再增加 Agent 子阶段 telemetry。

这样最大的好处是：**Phase 1 几乎没有架构风险，但页面体验会立刻发生非常明显的变化。**

如果只选一个本轮改版的核心验收标准，我会定为：

> **桌面端成功终态进入任务详情后，在默认视口内必须同时看到 Review 总结和第一条最高风险 Finding 的核心内容；无需先经过执行 Hero 或 Review Trace。**

这个比规定 Hero 必须多少像素、哪个区域必须多高，更适合作为实际验收标准。
