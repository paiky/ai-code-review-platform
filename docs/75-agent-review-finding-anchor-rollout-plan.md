# 75 Finding 原文定位与异步候选推进方案

2026-11-28。承接 71 的 A1A 离线定位、A1 终态定位和 C2A 取证中异步定位，将三项纳入第四方向。开发基线为 `main` 的 `d67f84a`，覆盖 `openai-unified-v2` 的 Chat Completions 和 Responses。 [71 审查引擎路线](71-review-engine-improvement-plan.md)

## 1. 推进条件与交付范围

**具备开发条件。** 73 已提供统一分组执行、组内共享期限、按遍审查与事实复核状态，以及按领取代次和递增版本更新的组内进度快照。74 已提供本遍新增 Finding 去重后的批量复核、冻结 diff 校验和正式结果回传。用现有本地替身可以验证定位插入点和混合版本兼容。真实 Provider、正式环境任务页和大 diff 的性能收益仍需用实际样本验证。 [73 实时进度与验收](73-agent-review-grouped-execution-rollout-plan.md#8-组内审查实时进度) · [74 组内事实复核](74-agent-review-fact-check-rollout-plan.md)

交付后，每组每遍按以下顺序执行：

1. **主审取证。** 模型可用 `submit_candidate` 提交候选和可选短引文，随后继续取证。Worker 在本地异步定位。
2. **正式提交与定位收敛。** 模型通过现有 `submit_review` 提交本遍结果，可引用候选或直接附引文。校验和去重后，在有限等待内处理本遍新增 Finding 的定位结果。没有候选的 Finding 可直接用同一定位器处理。
3. **事实复核与加审。** 复核仍使用本遍新增 Finding 和对应冻结 diff，沿用 74 的单次批量请求、裁决规则和预算。定位歧义、失败或超时只记录状态，复核按剩余组期限执行。每遍完成复核或跳过后再判断是否加审。整次任务汇总一份正式 Review Card。

A1A 先验证定位能力，A1 和 C2A 用同一定位器及终态契约，在一个可验收版本内交付。原因是直接引文是候选提交省略、队列饱和或引用无效时的回退，同时保持正常的 `submit_review` 收尾。C2B 的取证中逐条展示作为后续页面工作。 [71 的 C2B](71-review-engine-improvement-plan.md#c2b--执行过程显示增量候选评论)

## 2. 阶段一 · A1A 离线定位

- **改动量等级：小。** 范围限固定 diff、定位逻辑和离线验收。
- **目标与范围。** 复用现有 diff 文件及重命名归属解析。按文件、变更侧、hunk 和行号索引一次冻结 diff，同组多遍共用；多个候选复用索引。对连续短引文做文本匹配，兼容换行格式，保留空白与源码字符语义。只有同一 hunk 内可核实的连续坐标才能命中。指定 `OLD` 或 `NEW` 时只查对应侧。缺省侧时检查两侧，同路径同起止行的等价命中以 `NEW` 表示，存在多个不同坐标时标记歧义。重命名按命中侧返回该侧路径。
- **结果口径。** `MATCHED` 返回路径、侧和起止行，`AMBIGUOUS` 表示多处命中，`UNMATCHED` 表示可用材料内找不到，`UNAVAILABLE` 表示缺少可用材料或在执行边界内未完成。失败等情况使用有限的原因码。定位由 Worker 本地完成，每次审查可增加短引文输出，定位本身无需额外模型请求。
- **非目标。** 跨文件自动改挂、全文搜索兜底、调用模型重定位，以及修改正式 Finding 或页面。
- **验收。** 用人工标注的固定 diff 验证新侧、删除旧侧、重命名、同文件重复、两侧等价与两侧不同坐标、错引文、缺失或截断材料。加入大 diff 和多条引文，记录索引及定位耗时。逐条核对路径、侧、起止行和状态，歧义样本须能复现。
- **授权边界与停止点。** 本地固定样本即可开展。交付可复跑样本和逐条核对记录后可安全停留，算法接入留给阶段二。

## 3. 阶段二 · A1 与 C2A 接入统一执行

- **改动量等级：大。** 两种协议的工具契约、Worker 异步调度、逐遍复核、Backend 兼容回传及现有页面需要联动验收。
- **目标与范围。** 在 73 的统一执行器内完成以下工具、回传和展示，从正常 MR 或手动审查入口验收。

### 工具与收敛

- `submit_candidate` 只在主审取证阶段可用。接收组内路径、简短标题与说明、可选 `anchorQuote`。校验归属后返回候选 ID，定位交给有界队列。沿用 73 第 7 节的模型回合、上下文和收尾规则，有且只有 `submit_review` 可用于只允许正式提交的收尾轮。候选数量、引文长度和待定位工作受内部边界约束。
- `submit_review` 的 Finding 可带同一任务、领取代次、组及遍次的 `candidateId`，也可直接带 `anchorQuote`。同时提供两者时优先采用候选定位，正式引文供回退使用。候选定位只服务本遍校验、去重后保留的 Finding，文件归属不一致时按无有效引用处理。未知、重复或跨作用域的引用不得串到其他 Finding。未被本遍正式提交引用的候选无需阻塞复核，也不转成正式 Finding。
- 单次任务共用 2 个后台定位线程，最多容纳 64 个运行中及排队的定位，每遍最多登记 50 个候选，单条引文最多 600 字符。复核前只等待本遍新增 Finding 关联的工作，最多 500 毫秒，并受组剩余期限约束。组期限设为 `-1` 时仍使用 500 毫秒上限。队列满或异步结果未及时可用时，剩余定位预算允许直接引文回退，其余记录原因并继续。取消时停止派发并忽略迟到结果，重领后从冻结输入重新执行。
- 沿用 74 的批量复核。定位坐标可以随进度和结果供人工核对，事实裁决继续以冻结 diff 为依据。原文匹配成功和复核裁决使用各自的状态。

### 进度、终态和页面

| 位置 | 用户看到什么 |
|---|---|
| **执行过程 → 审查组 → 展开某遍** | 复用 73 的遍次快照。主审正式提交后立即按现有节奏回传新增 Finding；如定位尚在收敛，可显示「定位中」。收敛后显示定位状态、可核验坐标及本遍定位等待耗时，然后更新既有复核状态。短阶段可能在一次轮询中完成，遍次仍保留终态和耗时。 |
| **审查结果 → 展开 Finding → 上下文与判断依据** | 沿用 74 的布局，在「事实复核」前显示「原文定位」。唯一命中示例为「已核验 · 变更前 · `src/order.py:18–20`」。存在歧义、未匹配或材料不可用时显示对应状态。历史结果或无定位记录的 Finding 省略该行。卡片标题区、反馈和修复预览继续使用原 Finding。 |

取证期间的候选只按 C2A 供进度接口验收。复用 `groupPassProgress` 及终态补写，按 `runId + claimAttempt + groupId + passNo + candidateId` 关联候选，候选状态由 `PENDING_LOCATION` 进入 `LOCATED` 或 `UNLOCATED`，已关联或丢弃时分别记为 `FINISHED` 或 `DISCARDED`。定位状态作为独立字段保留。Backend 按领取代次和快照递增版本拒绝迟到、乱序数据。进度只回传有界的安全摘要、状态、坐标和原因码。 [73 遍次快照](73-agent-review-grouped-execution-rollout-plan.md#8-组内审查实时进度)

Worker 用可选 `anchorResults` 按最终去重后的 Finding 序号回传。Backend 核对领取代次、文件归属、坐标、重复或越界关联，使用现有结果附加信息保存。短引文留在 Worker 执行作用域，进度、终态附加结果和工具审计只使用核验所需的安全元数据。兼容缺字段的旧 Worker 和历史结果，沿用现有结果与进度 API。优先以现有 JSON 承载，本阶段不计划数据库迁移。 [现有审查结果 API](https://github.com/paiky/ai-code-review-platform/blob/d67f84a/backend-python/app/review_record/api.py#L75)

- **非目标。** C2B 的取证中逐条展示候选、替换正式 Finding 行号、把候选计入正式统计或提前发送通知。Claude Code、Anthropic Messages 和 Standard 沿用各自执行路径。
- **授权边界与停止点。** 本地或隔离环境走通正常入口、进度和正式结果，前端构建及浏览器验收通过后交付。发布时先使 Backend 兼容新旧回传，再更新 Worker 与前端，确认兼容 Worker 在线后再验收新链路。回退前收敛在途任务，历史结果继续由旧读端读取。生产发布和真实项目样本由用户安排。

## 4. 验收步骤与性能对照

1. **验证先定位后复核。** 用两种协议的替身从正常 MR 或手动入口分别跑单组和多组，至少一组触发加审。让一条候选的后台定位受控延迟，确认模型在定位完成前已收到候选 ID 并继续取证。每遍正式提交后，核对已引用候选先进入定位收敛，再发出本遍唯一一次批量复核；其他组可继续推进。另跑一遍仅带直接引文的结果。
2. **验证页面与终态。** 任务运行中打开「执行过程 → 审查组」，核对首审／次审的 Finding 定位状态与对应复核顺序，刷新后遍次和领取代次正确。任务结束后，核对一份 Review Card，在「上下文与判断依据」逐条比对路径、变更侧、行区间和反证。通过 `GET /api/review-tasks/{taskId}/code-quality-results` 验证最终去重后正确关联。再查历史任务、无引文的 Finding，以及反馈和修复预览。
3. **验证异常边界。** 覆盖队列饱和、预算不足、定位超时、多个命中、缺失 diff、无效或跨组候选引用、旧 Worker、取消、接管、乱序和重复完成。确认未引用的候选和历史领取代次都不会阻塞或写错正式结果。
4. **对照大 diff。** 固定 Base／Head、分组计划、模型和预算，分别使用普通 diff 与大 diff。用同一批冻结引文和同一替身响应分别走直接定位与异步候选，记录解析、定位、复核前等待和整任务耗时的 P50／P95，以及候选超时率、定位覆盖。大 diff 样本应证明候选可以和取证重叠，并且复核前等待不超过既定上限。再用同一真实 Provider 样本记录新增模型轮次、Token、引文提交率、错文件和错行，判断工具调用开销是否抵消等待收益。用实测记录具体边界及差异，标明替身和真实 Provider 的结果。

## 5. 与 Open Code Review 的差异

| 维度 | OCR `d4f568f` | 75 首版 |
|---|---|---|
| 提交和时序 | 审查中用 `code_comment` 提交原文并异步定位。每遍结束等待本组评论定位，再做复核。 | 取证时可提交候选，保留每遍正式提交。复核前只有限等待本遍实际引用的定位任务，直接引文走同一定位器。 |
| 定位范围 | 本文件按新侧、旧侧和新文件全文查找。可跨文件改挂，具备模型重定位回退。 | 限 Finding 所属文件的冻结 diff，核验变更侧和唯一坐标。歧义可追溯。 |
| 结果用途 | 定位写入评论的正式路径和起止行。 | 定位随终态 Finding 作为附加结果，并复用 73 的遍次进度显示核验状态。 |

## 6. 本地实施与验收记录

- 阶段一完成。离线样本覆盖新旧侧、重命名、重复片段、错引文及缺失和截断材料。25,000 行合成 diff 的首次索引加 50 次定位约 22 毫秒。
- 阶段二完成本地闭环。Chat Completions 与 Responses 均通过单组、多组、两遍、受控延迟、跨遍错误引用回退和 500 毫秒等待上限验收。本地还核对了定位队列饱和和取消后的入队行为。隔离 SQLite 以真实的手动 Agent 入队服务、Worker 领取／心跳／完成 API 和结果 API 验证，仓库工作树及模型使用替身。验证旧代次拒绝回写、快照重复及乱序、完成幂等，以及正式行号和复核结果与附加定位同时可查。
- 前端生产构建通过。用隔离接口生成的样本在浏览器核对「模型 Review → 执行过程 → 审查组」两遍的定位状态、等待和坐标，以及最终 Finding 详情中的「原文定位 → 事实复核」。
- 大 diff 对照采用每侧 6,000 行、直接与异步各 5 次本地替身运行。最后一轮复核前等待 P95 从 16 毫秒降至 0 毫秒，整任务 P95 从 463 毫秒增至 632 毫秒。两条路径使用相同的取证动作，异步多一次候选工具回合。真实 Provider 的总耗时、Token 和引文覆盖待按第 4 节验收。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File .\scripts\run-frontend.ps1 build
```
