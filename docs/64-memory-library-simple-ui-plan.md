## 2. 第一版的逻辑边界

### 2.1 上传字段与项目归属

- 第一版继续要求批次级“归属项目”，不实现参考图中的“暂不关联”。现有 `review_memory_sources.project_id` 非空，不能通过隐藏表单、虚构默认项目或悄悄绑定页面筛选项目规避。
- 用户操作字段为“归属项目、资料类型、适用端”；适用端提供明确的“不限”，不是必填具体端。资料类型提供代码规范、审查 Skill、架构约定，案例通过案例页维护。
- 文件标题默认使用文件名，简介可选；问题类型、路径、关键词、加载方式收进高级设置，默认沿用现有 ON_DEMAND。批次级默认值可应用于文件，文件行可单独修改类型和适用端；不为每个类型建立独立上传页。
- 文件的适用端沿现有上传 metadata 进入解析章节，不新增来源级端字段；发布前仍可逐章节调整。NULL“不限”和 GENERAL“通用端”保持原有不同语义。
- 新建仍保留原默认自关联；使用项目可在发布后通过既有关联入口管理。上传不自动共享、发布或开启项目记忆。
- “资料完全独立于项目、上传后再决定归属”是另一个数据模型专项，未经单独确认不进入本计划。

### 2.2 文件和发布流程

- 复用原单文件 multipart 上传、解析和草稿接口，批量行为由前端队列逐文件调用；不增加批量事务、后台导入队列或新的存储基础设施。
- 沿用 MD/TXT 单文件不超过 1 MiB、DOCX/文本 PDF 不超过 5 MiB；Skill 仅 Markdown，PDF 最多 100 页，不引入 OCR。参考图里的 100 MiB/50 文件不是本轮验收标准。
- 首版队列最多 20 个文件、合计不超过 50 MiB，串行处理；这是前端交互上限，服务端原校验始终有效，不增加管理配置项。达到上限时说明原因，不静默丢文件。
- 成功代表“已上传并生成草稿”，不叫“已生效”。用户逐份核对解析诊断和章节，沿原入口显式发布；不新增批量自动发布。

### 2.3 打标与案例

- 复用现有 `ReviewItemFeedback` 和记忆回写记录，不建立另一张打标池表，不复制反馈；任务详情现有“标记误报”入口保留。
- 本轮打标列表限定可由既有流程整理的 AI_FINDING / FALSE_POSITIVE，不能把所有旧规则卡片反馈或“有用”等评价都作为待沉淀误报。
- 显示“反馈状态”和“案例沉淀状态”两个事实，不将 VALID 当作案例已生成，也不将回写成功当作本次审查必定采用。已沉淀反馈仍可追溯，默认列表名称不意味着删除历史。
- 查看原任务、整理案例、查看案例沿原接口和人工确认流程；撤回/忽略沿原失效钩子停用案例并取消在途旧回写，不修改原 AI 结论。CONVERTED 等不可重复确认情形保留原限制。
- 不直接打开整个旧反馈治理页或全局启用 `VITE_REVIEW_LEARNING_UI_ENABLED`；新入口不连带开放旧策略转换、回放等其它功能。
- 最终跨项目反馈管理沿用现有可信管理部署边界，不新增账号/RBAC，不放宽项目正文或确认接口；从全局行进入操作必须使用该反馈真实 projectId。

## 4. U1：资料管理查询补齐

- **改动量等级：中。** 限 Python 资料管理只读模块，增补现有内部管理 GET 的有界字段与过滤，不改变旧默认响应语义或写接口，无迁移。
- **目标与范围：** 在服务端正确划分普通资料和案例，并批量返回来源的章节端摘要，让新列表不逐行请求详情、不在前端过滤单页伪造总数。
- **数据与接口：** 实施前先明确 DTO/OpenAPI。建议现有 `GET /api/review-memory/sources` 增加可选 `category=DOCUMENT/CASE`，DOCUMENT 对应 STANDARD/SKILL/ARCHITECTURE，CASE 对应 PITFALL/INCIDENT；省略时保留现行为。`kind` 与 category 同时提供时不匹配返回空，不扩大到其它类型。
- **摘要约定：** 仅管理列表条目增加有界 `targetTypes`、`hasUnrestrictedTarget`、`hasEntries`；类型去重，NULL 用独立标识表示“不限”，无章节明确展示“未设置”，不能误称全端。摘要按管理可见章节（包括草稿/停用）汇总，明确不代表已发布适用范围；既有端筛选仍按章节明确标签精确匹配。全局分页总数与分类过滤一致，旧项目摘要/引用详情不扩展。
- **非目标：** 端标签迁移、来源级新字段、文档树、写逻辑或检索规则变化；不借此清理旧查询。
- **验收方式：** 聚焦静态检查，随机隔离 MySQL/API 验证混合类型、类别与 kind 联合过滤、总数/分页、无章节/多端/NULL/GENERAL、管理摘要无正文、查询次数不随当前页行数增长；省略新参数保持旧查询结果。无需浏览器。
- **授权边界：** 用户已授权 U1，只实施上述只读能力，不改真实资料或开启记忆，不调用模型。
- **停止点：** 原页面不变且查询可独立使用；记录验收、本地提交，停止并等待 U2 授权。

## 5. U2：三 Tab 布局与简化上传

## 6. U3：批量上传队列

- **改动量等级：中。** 限 React 上传队列和原单文件上传调用，涉及多文件状态、重试和离开保护，无新后端契约或后台任务。
- **目标与范围：** 开放多选/拖拽，批次默认类型/端和逐文件覆盖；展示文件名、大小、类型、端、真实上传处理状态、错误、草稿链接及独立重试/移除。
- **队列约定：** 沿第 2 节数量/总大小上限串行处理。开始前锁定本轮归属项目及各文件有效设置；处理期间禁止修改当前提交元数据，提供“停止后续上传”，当前请求的落库结果仍单独核对。完成后成功文件保留 sourceId，重试不得重传已成功项目。
- **失败语义：** 单项明确失败不回滚前项成功，后续合法文件可继续；不自动重试写请求。网络超时/中断等无法确认结果的项显示“结果待确认”，提示先查资料，不能直接当作未写入或仅凭同名判断幂等。首版不新增持久化断点续传、自动去重或后台导入任务。
- **发布与导航：** 上传成功仍是草稿；从队列进入详情核对并显式发布，返回保留本页已成功结果。待上传文件/未保存设置有离开保护，上传中禁止无提示切页；刷新不承诺恢复本地文件，不能伪造刷新后继续上传。
- **非目标：** 批量事务、批量自动发布、放宽单文件限制、OCR、Skill 脚本执行、替换文件批量处理。
- **验收方式：** 前端 build、必须浏览器验收；混合规范/Skill 类型及格式、默认值与单文件覆盖、20 文件/50 MiB 边界、空队列、串行、部分成功、明确失败重试、结果不确定提示、停止后续、成功不重复提交、进入草稿发布、保存/离开保护和窄屏。隔离真实上传接口验证至少两份文件各建独立草稿且发布/关系不串项，无真实业务写入或模型调用。
- **授权边界：** 用户授权 U3 后实施；不增加服务端新写接口、迁移或长驻导入 Worker。
- **停止点：** 批量上传闭环可用；记录验收、本地提交，等待 U4。

## 7. U4：全局误报反馈只读查询

- **改动量等级：中。** 限 Python 反馈管理只读查询和独立 DTO，复用既有反馈/回写表，不改确认、撤回或 Worker，无迁移。
- **目标与范围：** 提供有界全局分页和项目/适用端/反馈状态/关键词筛选，为 U5 替代按项目列表做准备；当前 U2/U3 页面继续正常使用。
- **数据与接口：** 实施前先明确新独立管理 DTO/OpenAPI，建议 `GET /api/review-memory/feedbacks`；固定 AI_FINDING / FALSE_POSITIVE。可选 projectId/targetType/status/keyword，pageNo/pageSize 上限 100。旧项目反馈接口和详情/确认接口保持不变。
- **行摘要：** 包含真实 projectId、taskId、原问题摘要、打标原因、反馈状态、案例/回写状态及打标时间；不返回完整 finding 证据或原件。批量读取关联来源/最新回写，不复制旧列表的逐条查库。总数、筛选和分页基于同一一致性读取，关键词按字面有界匹配，稳定排序。
- **端与时间事实：** 先定位反馈关联任务/已保存运行输入中的权威端来源以及反馈时间字段，再固化 DTO 和查询。不能使用项目当前端配置推断历史任务；未记录的历史端为“未记录”，不猜测。若当前持久化事实不支持所需筛选，本阶段文档明确降级为未记录，而不是引入历史数据迁移或全量扫描 JSON；任何进一步扩围须重新确认阶段边界。
- **状态语义：** status 筛选使用真实反馈状态；回写 RUNNING/FAILED/SUCCEEDED 等另列展示，不拼造图中的单一“处理状态”。已确认但未生成案例仍非已沉淀；无效/已忽略/CONVERTED 保留追溯且沿原操作限制。
- **非目标：** 开放整个旧反馈治理系统、其它反馈类型、全局写接口、自动总结/确认、标签迁移、新权限模型或检索调整。
- **验收方式：** 静态检查、隔离 MySQL/API 验证多项目混合、筛选与总数、历史缺端、已忽略/旧策略转换/失败回写、无正文泄漏、有界查询、旧项目详情和确认边界；全局只读前后资料/反馈/开关无变化。无需浏览器。
- **授权边界：** 用户授权 U4 后只实施可信管理环境中的只读聚合，不写真实反馈、自动回写或触发模型。
- **停止点：** 新查询可独立验收，旧页面和接口不变；记录验收、本地提交，等待 U5。

## 8. U5：案例与打标全局视图及专项回归

- **改动量等级：中。** 限 React 全局反馈筛选、列表和既有案例抽屉集成，消费 U4，不改 Backend 或回写契约。
- **目标与范围：** 案例与打标页“待整理打标”默认全局分页，可选项目、适用端、反馈状态、关键词；显示原问题、原因、来源任务、反馈/沉淀状态、时间和操作。已沉淀案例继续用 U1 CASE 分类，不重复建数据池。
- **操作约定：** 从每行真实 projectId 打开原反馈详情，复用五段案例编辑、摘要/来源版本校验、人工确认、有界回写查询、失败重试/失效提示；忽略/撤回走原失效流程，不提供未经接口支持的单元格直接改标。来源任务和来源反馈可追溯，进入案例后使用其真实归属，不用页面项目筛选代替。
- **过渡收尾：** 去掉 U2 的选项目前置提示，反馈全局入口不依赖旧治理开关；项目使用配置原反馈入口仍可按该项目查看，避免破坏旧链接。反馈状态和案例沉淀状态始终分别展示。
