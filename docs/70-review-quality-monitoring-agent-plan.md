# 审查质量监测 Agent 推进方案

## 1. 目标与首版范围

将最近审查任务的人工排查变成可重复的质量监测。平台按期生成报告，指出问题发生在 Diff 读取、检索触发、搜索还是上下文注入，列出影响范围、可核对的样本和验收条件。负责人从报告进入原任务，确认归因、提出修复并关联验证结果。后续报告继续观察对应信号。

本专题治理的是**平台的审查机制**，包括 Planner、Retriever、Context Pack 和 Agent 取证工具。业务仓库中单条 Finding 的补丁和复审已有独立方案。M0–M4 已在本地或隔离环境验收。M5 已加入可手动触发的 GitHub Actions 工作流，待远端实跑。M6 已接入后续运行的镜像源码版本记录和报告对比，待真实部署样本验证。M0–M3 构成产品首版。 [Review 自动修复与复审闭环](69-review-auto-fix-loop-plan.md)

平台通过「设置 → 全局设置 → 审查质量监测」统一启停。开启后所有项目均可使用，用户在监测页选择本次查看、生成或对比的项目。确定性程序统计和排序，报告生成无需模型调用。定期提供修复思路的 Agent 按第 6 节独立推进。

## 2. 监测信号与优先级

| 方向 | 复用数据 | 首版判定与口径 |
| --- | --- | --- |
| Agent Diff 补取覆盖 | 任务触发类型和固定提交、`AGENT_QUEUED` 的纳入文件数与 Diff 字节数、隔离回放 | MR 和 Push 分开统计。同一固定版本对比补取前、此次补齐、补取后可读的文本 patch 数。可确认的二进制与未补齐原因（例如预算不足、提交不可用）单列。现有入队大小只能佐证输入变化。缺少补取计数或来源时，靠固定版本回放确认覆盖率，线上统计记为未知。 |
| Agent 分页取证和恢复 | Agent Run 安全审计、`AGENT_TOOL_ACTIVITY`、`AGENT_CONVERSATION_TURN` | 实际发生分页调用时，统计成功且返回内容的次数和行数，并用有结果计量的成功调用作分母计算成功空读率。patch 缺失、越界和其他读取异常单列。未调用分页的 Run 标为未验证。按同一次领取关联请求及返回区间，并观察连续无新增证据和后续源码读取或搜索恢复。旧事件缺少原因时记为未知。是否读到补齐的 patch 由隔离回放或已有的版本对照确认。 |
| Agent 首轮体积与审查终态 | `AGENT_QUEUED`、`AGENT_CONVERSATION_INPUT`、Agent Run、正式 Review 结果 | 分列入队 Diff 字节、内联或按需分页模式、可观测的首轮请求字节、Run 总耗时、成功或降级、正式结果指向的 Run 和 Finding 数。分页模式下首轮内联 Diff 为 0 仍可能有可读 patch。体积、耗时、正式终态和 Finding 变化分别对比。 |
| Standard 上下文 | `CONTEXT_PACK_BUILT`、`LOCAL_CONTEXT_RETRIEVED`、`LOCAL_CONTEXT_RETRIEVE_FAILED`、规则缺口聚合 | 分别统计已触发且零命中、命中范围过宽、有候选但保留为零，以及明确的预算裁剪。用 Context Pack 的实际 Prompt 字符数 `promptLength` 与目标 `maxTotalChars` 单独计算超目标，纳入 #2522 的对照。有明确触发条件的样本才能复核 Planner 漏触发。事件缺失时标为待回放。 |
| Finding 复核 | 正式 Review 结果、反馈、`EvaluationCase` | 将 `MAJOR` 或更高等级、证据为 `PARTIAL` 且高置信的结果列为复核候选。另从有已知风险信号或取证异常的零 Finding 任务抽样。实际误报、漏报和等级偏差依据人工确认的样本统计。 |
| 模型调用可靠性 | Agent Run 失败阶段、已记录的 Provider 错误、历史排查批次 | 统计可归因的首轮请求失败和后续任务恢复，按各自批次保留 Run 数和受影响任务数。可确认时再细分 HTTP 状态、超时和重试。缺少单次模型请求失败或重试事件时记录覆盖缺口。 |
| 监测数据完整性 | Agent Run 汇总、`AGENT_CONVERSATION_TURN`、历史排查批次 | 分别记录汇总轮次为 0、用量缺失和有用量事件的 Run 数。仅在两侧均可观察且属于同一次领取时核对一致性。无轮次汇总的记录不参与用量或效率结论。 |

默认观察最近 7 个完整自然日，按 `Asia/Shanghai` 计算日期边界，查询和持久化使用 UTC 的左闭右开区间。任务与 Run 按各自终态时间计入对应指标，诊断事件归属于被计入的 Review 或 Run。已知异常、正常和未知分别计数，同时展示窗口内符合条件的记录数、实际可度量数及异常数。按项目和引擎出独立行，已有模型或版本字段可用于分组，缺失版本归为未知。首轮历史样本与上线后的新规则分别形成基线。

线上修复对照优先固定 MR 的 Base/Head 或 Push 的 Before/After，并记录实际部署的 Backend 和 Worker 版本、模型及配置。版本或配置无法核实时标为不可比。首轮请求缩小后仍分别观察总耗时。Finding 数变化只用于选择复核样本，正确性由人工裁决或已标注样本判断。

任务影响范围按 `taskId` 去重。Agent 调用按 `taskId + reviewKey + runId + claimAttempt + sequence` 去重，轮次按同一作用域的 `turn` 去重。审计摘要与进度事件描述同一调用时只取一份可关联事实。Standard 以 `taskId + reviewKey` 定位结果，存在多次执行时取可明确关联到所选结果的事件。关联不可靠时将该诊断记为未知。历史进度被覆盖或清理时，报告继续保留生成时的统计事实，原事件链接显示当前可用情况。

优先处理可复现的错误证据、关键证据缺失或审查结果受影响的问题。证据强度相同的情况下，按影响任务数、覆盖的范围和最近是否持续发生排序。旧记录原因不明、样本少或只有代理指标时进入待复核。文件命中数反映搜索范围，预期证据的命中和保留才用于评估检索质量。

## 3. 平台入口、报告存储与接口

### 3.1 页面

全局开关开启后，现有「质量治理」导航隐藏时，侧栏直接显示「监测报告」。页面支持项目选择、报告历史、生成、指标、问题处置和对比。报告详情按优先级显示问题、影响任务数、可度量分母、代表任务、归因状态、负责人和验收条件。任务链接尽可能定位到对应 Review、Run 和执行过程，另提供已关联评估样本和回放记录的链接。

### 3.2 MySQL 持久化

| 记录 | 最小内容与一致性 |
| --- | --- |
| 报告运行及快照 `review_quality_monitor_reports` | 观察范围、起止时间、触发来源、幂等键、规则版本、运行状态、生成时间、错误码及有界快照。快照保存分母、异常计数、缺失覆盖率、问题摘要和代表记录引用，完成后固定。人工另发请求可生成新的快照。 |
| 改进问题 `review_quality_monitor_issues` | 稳定问题键按项目、引擎、问题类型和诊断子类生成，证据不足时使用统一的未知分类。记录首次与最近出现时间、最近报告、负责人、状态、关闭时间、验收条件及关联的评估或回放编号。各期报告引用同一问题，生成报告更新观测事实。只有关闭后新发生的异常才重新进入待复核。 |

采用 MySQL 5.7 兼容的加法迁移。成功快照与问题归并在同一事务提交，失败留可读的运行状态及错误码。手工重复提交同一请求和调度重复执行同一周期均只建立一次运行。重启后在可恢复的运行边界重试，同一运行的成功快照只可发布一次。报告结果保存脱敏计数、原因码和记录引用，完整源码、Diff、Prompt、凭据和任意模型输出留在报告存储及响应的白名单之外。

### 3.3 拟议接口及访问边界

| 接口 | 用途 |
| --- | --- |
| `GET /api/review-quality/monitoring/reports`、`GET /api/review-quality/monitoring/reports/{reportId}` | 分页查询指定项目的运行历史，以及指定报告状态、覆盖率和固定快照。 |
| `POST /api/review-quality/monitoring/reports` | 按所选项目和观察区间生成报告，接受请求幂等键，返回报告运行 ID 和当前状态。 |
| `GET /api/review-quality/monitoring/issues/{issueId}`、`PATCH /api/review-quality/monitoring/issues/{issueId}` | 查看问题当前状态，受控更新负责人、裁决、处理状态、验收条件及已存在的样本或回放引用。写入时核对版本，避免覆盖并发处置。 |

服务端检查全局开关，关闭时监测接口不可用。开启后沿用平台现有访问方式，取消固定项目和专用令牌。记录 ID、评估样本和回放的归属按所选项目校验。采集器只读已迁移的业务数据，生成报告只写本专题的报告与问题记录。

## 4. 从报告推进到修复

1. **发现。** 监测器筛选记录，生成报告并归并到稳定问题。每条问题附本次异常数和分母、代表任务、可核验事实或假设，以及预计在哪一层验证。
2. **确认。** 负责人从任务执行过程复核，选择可重现的固定样本，登记问题和验收条件。有争议的 Finding 沿用「评估样本」记录人工裁决。缺少原始提交或实际证据时留在待复核，并列出材料缺口。
3. **修复和回放。** 工程师修复审查机制，在受控工作区固定 base/head、工具或应用版本及相关配置，比较基线与候选。Diff 取证核对文件归属、可读内容及原因码。Standard 核对既定关键证据是否进入最终 Prompt、预算是否满足。回放摘要及版本挂回原问题。首版由工程师运行，后续接自动执行器。现有评估 Run 创建入口只初始化 `PENDING` 记录。
4. **观察和关闭。** 上线后在相同项目、引擎与可比较版本或配置下看异常率、覆盖率、耗时及复发。负责人结合回放和线上观察确认关闭。后续报告在关闭时间之后观测到同一问题的新异常时自动标记复发。相邻窗口可能包含同一条历史记录，每期独立计数，复发判定使用异常实际发生时间。

问题状态为「待复核 → 已确认 → 验证中 → 已关闭」。复核认定无需修复时可标记「已排除」并记录理由。回放失败保留在验证中，报告自动发现的事实和人工裁决分别显示。

| 首批样本 | 最小验收 |
| --- | --- |
| Agent MR #2538（#2536 为分段回放的同版本对照） | 验证固定版本原有 100 份 patch 保留并补齐 85 份。线上 #1088 入队 Diff 从 191,418 增至 397,830 字节，10 次分页全部成功并返回 1,254 行。首轮请求约从 221 KB 降到 24 KB，总耗时从 37.1 秒增至 80.4 秒，正式结果指向本次 Run。 |
| Agent Push #2472 | 历史 #1022 保留两次原因未知的空读。#1089 区分两次缺失和后续源码、搜索补证。隔离回放保留原 79 份并补齐 22 份文本 patch。线上 #1091 入队 Diff 从 283,492 增至 437,266 字节，9 次分页全部成功并返回 1,753 行。首轮请求约从 308 KB 降到 14 KB，总耗时接近。Finding 从 1 条变为 0 条，列为待人工复核。 |
| Standard #2510 / #2511 | 将同一 Diff 的两次执行作为回放参考。分别核对触发、检索和注入，确认候选在相同 6,000 字符预算内同时保留删除位置附近源码与关键实现证据。 |
| Standard #2522 | 宽检索后引用片段保留为零与 Context Pack 超过 6,000 字符裁剪目标分别报告。两种现象分别核对候选质量和预算裁剪边界。 |
| Finding 质量 | 复核有明确证据缺口的高风险 finding，再抽查零 Finding 任务。只有人工确认的判定进入误报、漏报和等级偏差评估。 |

业务仓库的材料仅在已有授权的隔离环境复用。样本不可访问时，可以合成等价夹具完成本地功能验收，历史复现单独记录为待验证。模型判断质量若需真实模型对照，单独约定样本、Provider 与预算。表中线上数据来自原排查的已完成验收，本计划实施时应核对对应 Run 和字段可用性。 [原排查与线上验收](thread://01a2116c-4f3e-7c92-a37c-09b56b7f2830?hostId=local)

## 5. 实施阶段与停止点

### M0 · 离线监测基线

- **改动量等级：中。** 需要对齐 Agent 与 Standard 多个数据来源并核对历史样本，使用一次性离线输出。
- **目标与范围**　输出一份结构化报告和可读摘要，覆盖第 2 节信号、分母、未知原因与代表记录。对照现有 Agent 观测和 Standard 规则缺口聚合，记录需要补采的字段。
- **非目标**　平台持久化、页面、调度、生产模型调用和修复审查引擎。
- **验收**　用第 4 节样本核对 MR 与 Push 的补取和实际分页、首轮体积及终态，保留 #2472 的旧记录和恢复过程，复核 Standard 的检索注入与超目标现象。清单标明哪些字段可直接汇总、哪些只可依靠回放恢复、哪些需补采。样本替代时区分夹具结果与历史结论。
- **授权边界与停止点**　只在可用授权内读数据，报告生成于本机或隔离环境。交付离线报告及数据缺口清单，停在任何数据库或页面变更之前。

#### M0 离线执行与数据缺口

报告脚本接受已脱敏的固定样本 JSON，输出 `report.md` 和 `report.json`。随仓库提供的样本来自既有历史验收，包含已核对的线上摘要及隔离回放。两类证据分别保留，独立历史批次按各自分母展示。

```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File scripts/new-review-quality-monitoring-report.ps1 -InputPath docs/70-review-quality-monitoring-baseline-input.json -OutputDirectory .local/review-quality-monitoring-historical
```

| 数据 | 可用性与 M0 处理 |
| --- | --- |
| Agent 取证和结果 | 只读进度与结果接口可提取入队 Diff 大小、分页模式、首轮请求大小、分页调用和正式结果。按 Run 和领取代次关联。旧记录或协议缺字段时保留未知。 |
| Diff 补取覆盖 | 已有回放可验证原有和补齐的 patch 数、正确文件和读取结果。只有入队字节和返回行数的线上记录保留为佐证。直接计算线上覆盖率仍需要可关联的补取计数和原因。 |
| Standard 检索与预算 | 从 `CONTEXT_PACK_BUILT` 和本地检索事件提取查询、匹配、候选、保留与字符数。摘要裁剪可能移除目标字符数，例如 #2522 的当前事件，报告按缺失呈现。删除附近源码和关键实现实际进入 Prompt 由隔离回放核对。 |
| Provider 可靠性 | 历史批次有六次首轮失败。完整的 HTTP 状态、超时子类型、成功重试前的失败和逐次请求重试次数需要结构化请求事件才能统计。 |
| Run 汇总一致性 | 可对照 Run 汇总和同轮事件。历史最近 50 个 Agent 任务涉及 56 次 Run，汇总轮次均为 0 且用量为空，其中 16 次 Run 留有带用量的轮次事件。隔离汇总时保留有事件和无事件的覆盖差异，修正落库另行处理。 |
| Finding 质量 | 报告筛出 Finding 归零的对照，以及 `MAJOR` 及以上、`PARTIAL` 且 `HIGH` 置信的结果作为人工复核线索。精确误报率、漏报率和等级偏差要使用已标注样本。 |

**M0 验收记录（2026-11-26）**　由既有验收样本生成历史报告，另从任务进度和结果接口的只读响应提取 11 次 Agent Run 和 3 条 Standard 记录，现场观测报告单独生成。

- **Agent。** #2538 的 Run #1088 分页 10 次、返回 1,254 行，#2472 的 Run #1091 分页 9 次、返回 1,753 行。两次 Run 均与当前正式结果关联。#2472 的两次历史空读、后续缺失原因和换工具恢复保留各自的记录，Finding 从 1 条变为 0 条待人工核对。
- **Standard。** 线上 #2510/#2511 仍是零查询记录，5,878 字符及两类关键证据来自既有隔离候选回放。线上 #2522 可核对 8 次查询、命中 6,978 个文件、0 个候选、0 个保留片段与实际 21,901 字符。线上事件的预算目标因摘要裁剪缺失，超目标的对照采用记录完整的历史样本。
- **运行观测。** 现场样本 11 次 Run 的终态均汇总为 0 轮，其中 7 次 Run 留有带用量的轮次事件。历史批次的首轮失败单独列出，当前任务样本缺少逐次模型请求事件，无法对比首轮失败率。
- **Finding。** 只读结果中 6 条正式 Finding 的等级、上下文状态和置信度均可核对，符合高风险、部分上下文和高置信组合的为 0 条。#2472 仍保留单独的归零复核项。
- **验证。** Windows PowerShell 5.1 生成两种来源的报告。人工夹具核对重复事件去重、领取代次隔离、成功空读率的分母、零和未知的区分，以及白名单过滤。未运行单元测试、触发生产 Review 或改动业务数据。

### M1 · 报告持久化与查询接口

- **改动量等级：大。** 涉及 MySQL 5.7 兼容迁移、公开接口、快照一致性和服务端访问控制。
- **目标与范围**　建立报告和问题表、手动生成及查询接口、问题处置接口。复用 M0 聚合能力，提供可独立验收的手工生成入口。
- **非目标**　前端导航、定时调度、回放执行器和历史报告批量回填。
- **验收**　隔离 MySQL 核对加法迁移、重复请求、失败及重试、问题归并、并发处置和项目越权。检查历史快照可读且输出不含报告白名单之外的数据。

### M4 · 隔离回放自动执行

- **改动量等级：中。** 需要把两种确定性回放接到已有评估 Run 和问题记录，并验证失败与历史兼容。
- **目标与范围**　负责人确认样本和验收条件后，通过受控命令触发隔离执行。自动跑 Diff 读取与 Context Pack 构建，写回基线、候选、版本和失败原因。复用评估 Run 的状态及结果记录。
- **非目标**　自动修改审查策略、真实 Provider 批量复审，以及从监测结果触发业务仓库写入。
- **验收**　固定相同提交、配置和预算，分别复现 Agent 与 Standard 样本。覆盖材料缺失、执行超时、重复触发及旧 `PENDING` 记录的兼容。验证运行结果可回到原问题核对。
- **授权边界与停止点**　只执行已授权样本的只读回放。两种回放可独立复核后结束本阶段，CI 尚未介入。

**M4 隔离回放。** 为材料仓库准备干净的固定提交工作区，将 `LOCAL_REPO_WORKSPACE_ROOT` 指向其隔离父目录，使用无自定义 ripgrep 配置的执行环境。夹具给出完整 Base/Head、纳入的文件，以及 Agent 分页期望散列或错误码，或 Standard 预期含源码片段的文件及字符目标。相同夹具在基线和候选平台版本上分别运行。命令仅输出测量值、夹具散列和版本。Standard 验收确认目标文件的源码片段进入最终 Context Pack，精确符号归属仍由回放样本复核。

```bash
python -m app.review_quality.monitoring_replay run --fixture fixture.json --worktree /isolated/source --build "$PLATFORM_SHA"
python -m app.review_quality.monitoring_replay record --baseline baseline.json --candidate candidate.json --run-id RUN_ID --item-id ITEM_ID
```

`record` 使用已迁移的数据库写回同项目 `REVIEW_REPLAY` 的待处理条目，项目从评估 Run 读取。命令核对夹具一致、测量值完整和候选结果。同一输入可安全重复导入，先前结果与本次不一致时拒绝覆盖。报告的问题详情可关联对应评估 Run。已使用固定提交的合成 Java 仓库验证分页内容散列、越界、Standard 两个证据文件同时保留，以及隔离评估记录的入库、汇总和幂等。

- **授权边界与停止点**　只对已授权项目做版本观察。负责人根据回放和报告确认是否关闭问题，完成一个试点问题的闭环后复核推广条件。

**M6 当前能力。** 页面支持选取同项目、同统计规则版本、等长且不重叠的成功报告。比较显示两侧覆盖率与指标差值，缺失或覆盖口径不同的指标标记待复核。离线打包从干净的构建输入取提交 SHA 并写进 Backend 与 Worker 镜像。手工构建可从当前干净的源码版本显式传递 `REVIEW_RELEASE_SHA`。缺少可验证源码 SHA 时省略版本记录。Agent 对比要求首次领取运行的入队与终态 Backend 一致，并记录终态 Worker 版本。Standard 按构建 Context Pack 的 Backend 版本记录。报告按引擎判断两侧是否都来自不同的单一版本或版本组合。历史、混合和截断样本可继续按时间窗口查看。真实试点验证需要两期部署记录和一个有回放证据的实际问题。

## 6. 后续方案：修复建议 Agent

Agent 定期为监测问题提供修法思路。它读取已生成的报告及问题历史，根据确定性采集事实提出可检验的假设。负责人在「监测报告 → 问题详情」查看建议、选择修法并结合回放决定是否关闭问题。现有报告继续由规则生成，模型失败时也可以查看报告和处置问题。

### 6.1 运行与输出

- 建议每周一北京时间 10:00 运行一次，消费最近一轮成功报告中新增、复发或影响明显扩大的未关闭问题。以实际出现的异常和样本更新为触发，重叠观察窗口重复纳入的同一事件沿用已有建议。
- 按项目读取白名单字段，包括诊断码、样本数与分母、代表记录引用、安全取证事实、人工处置摘要和回放结果。模型仅能引用本次已提供的记录。完整源码、Diff、原始 Prompt、凭据和其他项目资料留在原有记录中。
- 每个问题生成一条有版本的建议，字段包括观察事实、引用、待验证原因、最多三项修法、预期影响、最小回放样本和验收条件。证据不足时返回待补证及缺失材料。从同一问题和证据摘要派生幂等键，增加证据才产生新版本。建议与人工处置独立保存。
- 单轮按优先级限制分析问题数和模型预算。失败保留安全错误状态，后续可按原样本重试。关闭总体监测后停止选取新问题，建议调度单独启停。第一轮只在隔离环境运行，方案不创建生产定时任务。

### M7 · 离线验证建议质量

- **改动量等级：中。** 涉及问题材料选择、结构化输出和代表样本的人工作业对照。
- **目标与范围**　以 #2472、#2522 和一条无足够证据的样本验证事实引用、修法粒度及回放可执行性。为 #2472 保留异常恢复及 Finding 待复核，为 #2522 区分宽检索、零候选与超预算三类信号。
- **非目标**　生产模型调用、平台持久化、自动改代码和发布。
- **验收**　人工核对引用可定位、原因推断有标记、建议可用同一固定提交验证。无足够证据时能明确列出待补证项，模型生成的无效引用被拒绝。
- **授权边界与停止点**　只使用可读取的脱敏样本和隔离执行环境。交付建议样本、模型接入契约和规则验收结果，等待平台阶段。

### M8 · 建议入库与问题详情

- **改动量等级：大。** 涉及建议存储、API、模型调用入口和前端详情，需分开核对生成与处置语义。
- **目标与范围**　已有问题支持手动生成修复建议，保存建议版本、证据引用和处理状态。页面可看最新版本、回放条件和建议生成失败原因。
- **非目标**　模型自动修改报告、人工裁决、平台代码或配置，以及批量生产回放。
- **验收**　隔离环境验证按项目关联、重复请求、模型超时、输出不合规和建议版本切换。已有报告和人工处置独立可用。
- **授权边界与停止点**　真实模型仅在已授权环境和预算内调用。先交付手动闭环，暂停新增入口时保留历史建议。

### M9 · 定期生成与效果复核

- **改动量等级：大。** 涉及部署调度、模型费用、失败恢复及后续回放关联。
- **目标与范围**　按周处理满足触发条件的问题，汇总产出、失败和已获人工复核的情况。负责人可将建议关联评估 Run，核对已执行验证和上线观察。
- **非目标**　自动修复、自动合并或发布、钉钉外发和自动关闭问题。
- **验收**　隔离验证定时重复触发、预算与上限、全局关闭、失败重试和异常复发，选择一个有固定样本的问题核对从建议到回放结果的关联。
- **授权边界与停止点**　生产调度按部署授权启用。负责人确认修法与最终效果，暂停建议调度即可停止后续生成。
