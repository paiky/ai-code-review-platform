## 一、平台概述

### 1.1 项目建设目标

本项目面向研发变更质量管理场景，建设可接入 GitLab、钉钉和 AI 模型 Provider 的 AI代码质量审查平台。平台通过“规则优先、AI 增强、结果留痕、通知闭环”的方式，把分散在 Merge Request、Push 和人工检查中的质量风险统一沉淀为可追踪的审查任务、提醒卡片和 AI finding。

项目一期重点解决以下问题：

- 研发变更缺少统一接入、分析和追踪入口。
- 接口、数据库、缓存、MQ、配置等高价值变更容易被遗漏。
- 代码审查结论缺少结构化证据、通知闭环和历史留痕。
- AI Review 缺少基础配置、执行、结果展示和失败重试能力。

### 1.2 一期能力概述

一期已经形成从变更接入到结果查看的基础闭环，并具备标准 AI Review 能力：

```text
GitLab MR / GitLab Push / Manual
  -> Diff 与 changed files 获取
  -> 规则分析
  -> 结构化提醒卡片
  -> 标准 AI Review（按配置触发）
  -> 钉钉通知或明确记录跳过原因
  -> 任务、结果和通知落库
  -> 前端任务列表与任务详情查看
```

经现有代码、接口、页面入口和自动化测试证据核对，一期约定范围已经具备验收基础。正式验收按照第二章所列范围、标准和证据执行，生产环境连通性由现场验收验证。

### 1.3 平台能力全景

| 能力域 | 完整能力方向 |
|---|---|
| 变更接入 | GitLab MR、Push、手动审查、Diff 补拉与回退 |
| 规则提醒 | API、DB、缓存、MQ、配置识别，规则模板和提醒卡片 |
| AI Review | 标准 AI Review、多模型、证据增强、Agent Review |
| 通知协同 | 钉钉通知、跳过原因、失败留痕和平台详情 |
| 任务管理 | 任务列表、详情、结果、进度、通知、重试和调度 |
| 质量治理 | 评估样本、回放、质量看板、规则缺口和验收门禁 |
| 平台配置 | 项目、项目组、Provider、Profile、Prompt 和多端策略 |
| 运维与安全 | 队列、脱敏、清理、成本、安全治理和发布门禁 |

分期能力概览：

| 阶段 | 建设主题 | 能力描述 |
|---|---|---|
| 一期 | 基础闭环与标准 AI Review | 完成变更接入、规则分析、提醒卡片、标准 AI Review、钉钉通知、数据留痕和前端查询 |
| 二期 | AI Review 增强与规模化 | 建设多 Provider、多模型、Push 智能触发、调度队列、详细进度、修复预览和多端配置能力 |
| 三期 | 高准确证据链与质量治理 | 建设源码上下文检索、证据预算、确定性检查、finding 补证据、评估回放和质量治理能力 |
| 四期 | Agent 化与平台产品化 | 建设只读 Agent Review、真实样本验收、项目知识、专项检索、运维安全和团队质量策略 |

## 二、一期验收范围与标准

### 2.1 一期验收边界

一期固定验收“基础闭环 + 标准 AI Review”，包括：

1. 项目、项目组及 GitLab、钉钉、标准 AI Provider 的基础配置。
2. 接收 GitLab Merge Request Hook、Push Hook，并提供手动审查入口。
3. 获取 changed files 和 diff；MR 数据不足时支持 API 补拉，Push 支持 compare API 和 payload fallback。
4. 识别 API、数据库、缓存、MQ、配置等重点变更。
5. 按规则模板生成结构化提醒卡片，保留命中证据、文件位置、diff 和维护草稿。
6. 审查任务、原始事件、分析结果、提醒卡片、标准 AI Review 结果和通知记录落库。
7. 按配置发送钉钉通知；未配置、未命中或关闭通知时记录明确的跳过原因。
8. 通过任务列表、任务详情和基础设置入口查看结果、状态和配置。
9. 使用单个已配置 Provider 执行标准 AI Review，支持手动或 MR 触发、finding 展示、基础进度、失败信息和重试。

一期不验收多模型并行、高准确证据链、质量治理、只读 Agent Review、成本运维看板和合并门禁。这些能力分别纳入二至四期。

### 2.2 一期主要建设成果

| 编号 | 建设成果 | 完成说明 |
|---|---|---|
| P1-01 | 统一变更接入 | MR、Push 和手动审查均可进入平台任务流程 |
| P1-02 | Diff 获取与回退 | 支持 MR 补拉、Push compare 和 payload fallback |
| P1-03 | 重点变更识别 | 覆盖 API、DB、缓存、MQ、配置五类重点信号 |
| P1-04 | 结构化提醒卡片 | 提醒项包含类型、等级、证据、位置及维护建议 |
| P1-05 | 标准 AI Review | 单 Provider 可执行审查并保存结构化 AI finding |
| P1-06 | 钉钉通知闭环 | 支持发送结果或记录明确的 SKIPPED / FAILED 状态 |
| P1-07 | 数据留痕 | 任务、事件、分析、提醒、AI 结果和通知均可追溯 |
| P1-08 | 前端查看与重试 | 支持任务列表、详情、基础设置和任务重试 |

### 2.3 一期验收标准矩阵

| 能力域 | 验收标准 | 验收证据 |
|---|---|---|
| 项目接入 | 可维护项目及所属项目组，接入信息可用于后续审查 | 项目配置页面或项目接口返回 |
| MR 接入 | 合法 Merge Request Hook 可创建审查任务并保存原始事件 | Webhook 响应、任务详情、数据库记录 |
| Push 接入 | 合法 Push Hook 可创建审查任务，并取得 compare 或 payload 中的变更 | Webhook 响应、changed files、任务详情 |
| 手动审查 | 用户提交合法分支、提交或文件变更后可创建任务 | 手动审查接口响应和新任务记录 |
| Diff 获取 | 输入不完整时执行约定的补拉或回退；失败时保留可解释原因 | 原始事件摘要、changed files、失败信息 |
| 规则分析 | 至少可识别 API、DB、缓存、MQ、配置中的一种重点变更 | 分析结果及命中规则 |
| 提醒卡片 | 命中规则后生成结构化提醒项，并展示证据、位置和建议 | 任务详情提醒卡片、结果 JSON |
| 标准 AI Review | 配置一个可用 Provider 后可执行审查并保存 AI finding | AI Review 结果、基础进度及结果记录 |
| 通知闭环 | 可发送钉钉通知；不发送时记录明确原因，不出现无状态丢失 | 通知记录及请求摘要 |
| 查询追溯 | 可查询任务、原始事件摘要、提醒卡片、AI 结果和通知记录 | 任务列表、任务详情及相关接口 |
| 失败与重试 | 审查失败原因可见，任务可按现有入口重新执行 | 失败信息、重试响应及新结果 |

## 三、后续阶段建设规划

### 3.1 阶段总览

| 阶段 | 建设主题 | 建设目标 |
|---|---|---|
| 一期 | 基础闭环与标准 AI Review | 平台可接入、可分析、可审查、可通知、可追溯 |
| 二期 | AI Review 增强与规模化 | 提升模型配置弹性、触发效率和并行处理能力 |
| 三期 | 高准确证据链与质量治理 | 让 AI 结论更可解释，并能用样本持续衡量质量 |
| 四期 | Agent 化与平台产品化 | 完成受控 Agent、团队治理、运维安全和发布策略 |

### 3.2 二期：AI Review 增强与规模化

**建设目标**

从“单模型可用”升级为“多模型可配置、可调度、可按策略触发”，提高不同项目和不同端类型的适配能力。

**主要建设内容**

- 多 Provider 接入与统一配置管理。
- Profile、Prompt、模型参数及默认 Provider 管理。
- 项目组多模型配置、多模型并行执行和结果区分展示。
- Push 智能触发策略，包括分支、变更规模、风险命中和防抖控制。
- 调度队列、并发控制、失败恢复和详细进度展示。
- finding 级修复 Patch 预览。
- 项目端类型、目标类型路径映射及多端默认 Profile。

**预期价值**

- 支持按项目和场景选择模型，降低单一模型依赖。
- 将部分问题发现前移至 Push 阶段，减少 MR 后期返工。
- 通过调度和触发策略控制模型调用量、等待时间和重复执行。

**阶段验收条件**

1. 至少两个 Provider 可分别配置、连通并保存结果。
2. 一个项目组可配置多个 Review 模型，并在同一任务中区分结果。
3. Push 仅在命中配置策略时触发 AI Review，未命中时原因可解释。
4. 队列、执行进度、失败和重试状态在页面可见。
5. 修复预览只能生成和展示，不直接修改源代码。

**进入三期前置条件**

二期功能完成内部回归；选定至少一个真实项目完成多模型和 Push 策略验证；确认任务量、失败率和平均耗时处于可接受范围。

### 3.3 三期：高准确证据链与质量治理

**建设目标**

从“基于 diff 给出结论”升级为“基于受控源码上下文和确定性证据给出可解释结论”，并形成质量评估、回放和验收闭环。

**主要建设内容**

- 本地 mirror/worktree 及受控源码工作区。
- Context Planner 对变更信号、语言、端类型和证据需求的规划。
- Local Retriever 对调用关系、DTO、DB/Mapper、缓存等上下文的检索。
- Context Pack 预算、裁剪和未注入证据摘要。
- 首次 Review 前敏感信息扫描 Preflight 及失败降级说明。
- finding 级二次补证据和补证据过程可观测。
- 评估样本、Review 回放、质量看板、规则缺口归因和能力改动验收记录。
- 质量治理统一页面入口和管理视图。

**预期价值**

- 降低因上下文不足产生的误判和无证据结论。
- 用样本、回放和指标判断规则、Retriever 或 Prompt 调整是否有效。
- 为后续扩大使用范围提供可审计的质量依据。

**阶段验收条件**

1. 受控工作区可准备任务源码，失败和清理状态可追踪。
2. 高风险 AI finding 展示 evidence、contextStatus、confidence 和 missingContext。
3. 证据超出预算时明确说明哪些证据未注入，不把“未提供”等同于“不存在”。
4. 敏感信息扫描在首次 Provider 调用前执行，失败摘要经过脱敏。
5. 可创建人工评估样本，并在质量看板中按项目、Provider、Profile 和风险类型统计。
6. 规则或 Retriever 调整可通过回放和验收记录留痕。

**进入四期前置条件**

三期完成真实项目证据链验证；积累可用于对照的人工评估样本；质量看板可以解释主要误判、上下文不足和等级偏差来源。

### 3.4 四期：Agent 化与平台产品化

**建设目标**

在安全授权、真实样本和可回退机制下引入服务器侧只读 Agent Review，并补齐团队治理、平台运维和规模化发布能力。

**主要建设内容**

- 服务器侧只读 Agent Review、独立 Worker、加密 Key 和受限只读工具。
- Agent 失败时显式 STANDARD_FALLBACK，不把降级结果伪装为 Agent 成功。
- STANDARD / AGENT 对照观察、脱敏导出和真实样本准确率验收。
- finding 反馈、人工确认的项目知识及项目内策略治理。
- MQ、配置、测试覆盖、跨仓及前端调用方专项 Retriever。
- Provider 成本、耗时、失败率、队列、工作区和资源清理运维看板。
- 数据脱敏、安全审计、团队质量策略及可配置合并门禁。

**预期价值**

- 在明确安全边界下提高复杂代码变更的自主检索和分析能力。
- 将个人审查经验沉淀为可追踪、可回放的项目知识。
- 通过成本、质量和安全指标支撑平台规模化推广。

**阶段验收条件**

1. 仅明确授权的项目可启用 Agent Review，且源码外发授权可追溯。
2. Agent 只能访问当前任务受控工作区和白名单只读工具。
3. Agent 失败、超时或不可用时明确降级，标准 Review 主链路仍可完成。
4. 至少积累 30 条去重人工标注样本，并具备可解释的 STANDARD / AGENT 配对覆盖后，才能开展准确率扩大验收。
5. 成本、失败率、耗时、安全事件和资源清理状态可观测。
6. 合并门禁默认不自动启用，必须由项目策略和管理审批明确开启。

**完整产品验收前置条件**

完成授权项目的生产技术验收和真实样本质量验收；确认安全、成本、回退和运维机制可持续；根据验收结果决定是否扩大 Agent 授权范围及启用团队质量策略。
